# Найденные задачи по улучшению

## 1) Исправление опечатки
**Задача:** в `backend/app/purchases/finik_test.py` заменить `"PaymentId": f'payment_id'` на использование реальной переменной `payment_id` (например, `str(payment_id)`).

**Почему:** сейчас в payload уходит строковый литерал `payment_id` вместо UUID, что выглядит как типографическая ошибка в примере формирования тела запроса.

## 2) Исправление ошибки
**Задача:** разрешить конфликт миграций в `backend/app/courses/migrations/` (три файла с префиксом `0002_*`) через merge-миграцию или пересборку цепочки миграций.

**Почему:** наличие нескольких миграций с одним номером обычно приводит к нескольким heads в графе миграций и усложняет предсказуемый деплой/применение миграций.

## 3) Исправление комментария / несоответствия документации
**Задача:** уточнить комментарий в `backend/app/purchases/finik.py` рядом с путём `Path(settings.BASE_DIR).parent / raw`:
`# Try relative to project root (BASE_DIR is /app/app)`.

**Почему:** комментарий не совсем точен по терминологии: `BASE_DIR` — это директория Django-проекта (`/app/app`), а реально проверяемый путь строится от `BASE_DIR.parent` (то есть `/app`). Лучше явно отразить это в комментарии, чтобы избежать путаницы.

## 4) Улучшение теста
**Задача:** усилить `test_paid_course_allowed_after_purchase` в `backend/app/tests/test_api.py`:
- дополнительно проверить структуру и ключевые поля ответа (`id`, наличие модулей/уроков),
- добавить негативный кейс с покупкой в статусе `pending`/`cancelled`, который должен давать `403`.

**Почему:** сейчас тест проверяет только HTTP-статус `200`, из-за чего регресс в бизнес-логике доступа по статусу покупки может остаться незамеченным.
